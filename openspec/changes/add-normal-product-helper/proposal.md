# Proposal: Add normal_product() Helper Function

## Context

在处理顶点算符代数 (VOA) 的复合算符时，经常需要计算多个算符的嵌套正规序乘积。目前的 `NO(A, B)` 函数只支持两个算符，要计算多个算符需要手动嵌套调用：

```python
NO(A, NO(B, NO(C, NO(D, E))))
```

这种写法有以下问题：
1. **可读性差**：嵌套结构不易阅读
2. **易出错**：手动嵌套容易写错括号匹配
3. **不灵活**：算符数量变化时需要重写表达式

## Motivation

参考 Mathematica 的 `OPEdefs.m` 包和 VOA 研究中的常见需求，需要一个简洁的方式来表达多个算符的正规序乘积。这在以下场景中特别有用：

1. **W-代数**：构建高阶生成元需要多个算符的正规序
2. **Sugawara 构造**：从流算符构造应力张量
3. **复合算符计算**：任何需要多个算符正规序乘积的场合

## Proposed Change

添加 `normal_product()` 辅助函数到公共 API，支持任意数量算符的嵌套正规序乘积。

### 核心功能

```python
normal_product(A, B, C, D)  # → NO(A, NO(B, NO(C, D)))
normal_product(A)           # → A
normal_product()            # → One
```

### 转换规则

- 从右向左构建嵌套的 `NO`
- 自动处理特殊情况（零算符、单位算符、标量系数）
- 保持与现有 `NO()` 函数的语义一致性

## Design Rationale

### 为什么选择从右向左嵌套？

VOA 中的正规序乘积通常是右结合的：
```
(A B C) := (A (B C))
```

这种约定在 Thielemans 论文和 Mathematica 实现中被广泛采用。

### 为什么不直接修改 `NO()` 函数？

1. **API 稳定性**：`NO(A, B)` 已经被现有代码使用
2. **语义清晰**：`NO` 严格表示二元运算，`normal_product` 表示多元运算
3. **向后兼容**：添加新函数不影响现有代码

### 为什么需要单独的函数？

1. **可读性**：`normal_product(A, B, C, D)` 比 `NO(A, NO(B, NO(C, D)))` 更清晰
2. **灵活性**：支持任意数量的算符（包括 0 个和 1 个）
3. **工具函数性质**：这是一个便利函数，不是核心运算

## Risks and Mitigations

### Risk 1: API 污染

**风险**：添加太多辅助函数可能导致臃肿的 API

**缓解**：
- 这是常用的高层操作，值得包含在核心 API
- 文档明确标注这是便利函数
- 未来可以考虑移动到 `utils` 模块（如果需要）

### Risk 2: 语义混淆

**风险**：用户可能混淆 `NO()` 和 `normal_product()`

**缓解**：
- 文档清晰说明两者的区别和关系
- 示例代码展示何时使用哪个
- 类型提示确保正确使用

### Risk 3: 性能问题

**风险**：深层嵌套可能导致性能问题

**缓解**：
- 这只是语法糖，最终生成的嵌套结构相同
- 性能与手动嵌套 `NO()` 相同
- 用户可以选择是否使用此函数

## Alternatives Considered

### Alternative 1: 修改 `NO()` 支持可变参数

```python
NO(A, B, C, D)  # 修改现有函数
```

**拒绝原因**：
- 破坏 API 稳定性
- 语义不清晰（二元 vs 多元）
- 与现有代码不兼容

### Alternative 2: 使用中缀操作符

```python
A * B * C * D  # 重载 * 运算符
```

**拒绝原因**：
- Python 的 `*` 通常用于普通乘积，不是正规序
- 正规序是特殊操作，应该显式表达
- 与 SymPy 的表达式系统冲突

### Alternative 3: 不添加此函数

**拒绝原因**：
- 用户仍然需要手动嵌套 `NO()`
- 降低代码可读性和易用性
- 增加出错可能性
